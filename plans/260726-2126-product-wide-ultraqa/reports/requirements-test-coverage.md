# SilverSea PRD requirements-to-test coverage

Generated 2026-07-26 from the current test source inventory. This is a static coverage map, not a claim that the suites passed in this run.

## Interpretation and limits

- Scope: 66 numbered requirements / 332 section-level acceptance cases, 122 module-wide criteria, and Q01–Q23. The section count is 332 because M3.6 and M3.7 each define six cases; the other 64 sections define five.
- Every PRD requirement and Q01–Q23 remains **authority: pending decision**. A test proves only current implemented behavior; it does not approve a proposed customer rule.
- **Direct** means an automated assertion is named for the acceptance behavior. **Partial/no direct** means adjacent code may be tested, but the full case (especially UI, RBAC, concurrency, export, or cross-module reconciliation) is not directly proved.
- Browser/manual checks below are still required even when backend logic is directly covered.
- ROADMAP delivery labels are reproduced as planning context only; they are not fresh implementation or pass claims.

## Highest-risk direct-coverage holes

- **M1.7 all five cases:** no automated suite directly proves two-way load sequencing, overlap/load compatibility, cancellation, delay, or cross-day behavior.
- **M7.2 all five cases:** no automated suite directly proves attendance-day classification, calendar UI, leave/rest/holiday rules, role controls, or concurrent edits.
- **Responsive and visual acceptance is never fully automated:** M8.1 has only conditional driver-portal E2E coverage; every module’s HT-07 still needs real viewport review.
- Most case 04 RBAC/audit requirements and case 05 double-submit/concurrency requirements are only partially covered. Do not infer universal protection from shipment-specific RBAC, optimistic-lock, or idempotency tests.
