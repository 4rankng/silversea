## Changes

- Frozen debit-note customer receivables now agree across issued lines, document
  totals and the actual spreadsheet download. Existing issued documents remain
  unchanged. Known zero debt, unknown nonempty snapshots and legacy snapshots
  have distinct behavior.
- Customer customs charges are displayed separately from actual company costs.
  Financial create/retry commands use the existing durable transaction service;
  concurrent freight-adjustment requests cannot create duplicate pending rows.
- Invoice saves serialize pending submissions and keep a stable retry identity.
  Late search/detail responses cannot replace a newer selected shipment/trip.
- Accountant fee editing uses the correct entry identity and preserves the
  untouched side of a cost/charge pair. Only eligible unconfirmed rows can be
  voided. New rows use the canonical expense form with an explicit payer and
  configured fee, rather than fabricated amounts.
- Driver cost corrections preserve audit history and optimistic versions.
  Accounting sees the current amount alongside the original entered amount and
  confirms the current version. Confirmed costs remain protected.
- OPS pin/delete failures are visible and recoverable. Receipt-photo access uses
  the same owner and assignment rules as the expense workflow, with unrelated
  users still denied. Driver suggestions come from the configured active catalog.
- Deposit intake retains its estimated-amount meaning. Accounting can complete
  a blank amount, edit dates/notes before refund, and save an optional blank CV
  date. Positive whole-VND validation respects database precision; a minus sign
  is never stripped into a positive amount. CV +14 calendar days is editable.
  Refund/edit requests serialize and a full refund posts exactly once. The current
  UI sends the displayed amount; a concurrent amount change returns 409 with no
  posting and requires a fresh confirmation after refresh.
- Voided native OPS costs and their linked billing entries no longer contribute
  to live debit totals or new cost locks. Confirming an OPS cost no longer counts
  its customer charge again through the linked billing row. Historical frozen
  documents stay intact.
- Linked OPS, driver and invoice billing rows are read-only in the debit editor.
  The API checks and locks their canonical source before rejecting direct edits
  or deletes, preventing divergent financial copies. Manual/TRIP rows retain
  their existing editing behavior; guidance remains readable at narrow widths.
- Deposit history is visible across month boundaries, errors have recovery
  controls, and the existing stylesheet is loaded. Inputs, warnings, totals and
  narrow-screen forms now have their intended styling.
- Shared confirmation and customer drawers retain focus on close; nested row
  checkboxes/action buttons keep their keyboard behavior. Timestamps use the
  existing Vietnam formatter, long business identifiers wrap within their cells,
  and long driver names no longer collide with the month control. Accounting
  buttons use the shared design-system classes; date inputs and filter menus
  remain visible and contained at narrow widths.
- Customer database operations moved into a domain service without changing
  permissions, responses or idempotency namespaces. Invalid runtime configuration
  fails startup instead of silently selecting fallback databases or development
  settings. Route IDs reject trailing garbage and unsafe integers.

## Configuration and rollout

Port-filter visibility is now data: `dispatch_zones.show_port_facet` and the
administrator's **Hiện bộ lọc cảng ở kế hoạch tổng quát** setting. Runtime code
uses the flag, independent of a location's code, name, Unicode form or rename.
The one-time seed/backfill preserves the previous default display policy.
Existing public field names are retained where renaming would break clients.

Apply migration `20260922074926_dispatch-zone-port-facet.sql` **before** the new
API, then release the frontend. It adds one defaulted boolean and preserves the
legacy visibility policy as data. The migration was applied to an isolated copy
before the local browser and integration databases. The generated schema
snapshot also reconciles historical metadata drift; unrelated generated DDL is
not included. An application rollback can leave this additive column in place.

No production data correction or historical billing rewrite is included. The
container refund tracker retains the existing full-refund action; damage
charges/partial cash refunds require a separately defined accounting decision.
The separate shipment deposit-record form already tracks a recovered amount,
but saving that record does not itself post a cash receipt.
