Keep valid sessions through temporary identity service failures
QA-124 | P2 | Bug | TODO
Review date: 14 September 2026
Scope: Local source snapshot 9e09c901f5f7
Role: All signed in roles
Location: Application startup and GET /auth/me
Existing behaviour
A temporary HTTP 503 from /auth/me clears a valid token and returns no user. The router then sends the user to login, turning an identity-service interruption into a forced new sign-in.
Target behaviour
Keep valid credentials during temporary identity lookup failure. Gate protected content with an internet/service-required recovery state and Retry; clear credentials only for an invalid, expired or revoked session.
User impact
A brief service interruption interrupts every role and may force users away from their current work.
Cause and investigation
The client turns every non-OK response into ApiError. useAuth.tsx:122 clears tokens for any ApiError and returns null; retry:false suppresses recovery. Raw network exceptions do not enter this token-clearing branch.
Steps to reproduce
1. Start with a valid token; make cold-start /auth/me return HTTP 503.
2. Inspect identity and token storage, then restore the service. The isolated extracted function cleared the valid token.
Acceptance criteria
1. HTTP 503, 502, 429 and network errors preserve valid credentials while protected work remains blocked.
2. Retry after connection/service recovery restores identity without entering credentials again.
3. HTTP 401, expiry and actual revocation still clear the session and scoped data.
4. Cover startup failure and recovery separately from genuine authentication rejection.
Verification coverage
CODE-READ ONLY for the application. An isolated fetchAuthUser probe with HTTP 503 ApiError cleared a valid token. No staging UI, API or database reproduction; add a testplan regression before implementing.
