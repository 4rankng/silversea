Reconcile concurrent trip edits before retrying a version conflict
QA-134 | P1 | Bug | TODO
Review date: 14 September 2026
Scope: Local source snapshot 9e09c901f5f7
Role: Admin/Manager editing the same eligible trip in two sessions
Location: https://vantai.tingting.vip/trips/:id/edit
Existing behaviour
The editor sends populated fields, including values the user did not change. On a 409 it fetches the current trip but uses only the new version number; the retry retains the earlier payload. For example, editor A opens version 3 with revenue 1,000,000; editor B saves revenue 2,000,000 as version 4. A changes only notes and saves. The first request correctly conflicts, but the automatic retry can replace B's revenue with A's old 1,000,000 without presenting the conflict. This follows the source path and has not been reproduced against staging.
Target behaviour
Preserve the user's draft and require reconciliation when the record changed. Show the current values and local changes, or safely merge fields proven unchanged since the original snapshot. Never substitute a fresh version solely to force a stale full payload through the concurrency guard.
User impact
Concurrent edits can silently overwrite accepted financial or operational changes, leaving plausible values and a successful save rather than an actionable conflict.
Cause and investigation
Confirmed source behavior: the retry closes over the old payload and replaces only its version. The backend's version guard works on the first request; refetching a version does not establish user intent for the other changed fields.
Steps to reproduce
1. Proposed controlled regression: two isolated sessions open the same CREATED trip with valid required fields and a nonzero revenue split. Keep A's editor on its original snapshot.
2. B changes and saves that revenue split. A changes only notes, then saves. Record both PUT payloads and the final revenue readback.
3. Repeat with both users editing the same field, with an unrelated 409 business conflict, and with another update during reconciliation.
Acceptance criteria
1. An edit 409 never triggers an unchanged full-payload retry with only the new version. Non-version business conflicts are explained without blind retry.
2. Keep A's local draft visible and B's committed values intact. Any merge compares original, local and latest values; conflicting fields require an explicit choice by the current editor.
3. A reconciled save uses the version actually reviewed and still rejects another concurrent update. This is edit conflict handling, not an internal approval workflow.
4. Add a hook regression capturing both requests and prove B's changed revenue survives A's notes edit. Then verify two-session UI and persisted readback for CREATED and another ordinarily editable state; no approval gate is introduced.
Verification coverage
CODE-READ ONLY. The source path was reviewed; the current staging deployment, UI interaction and database side effects were not exercised for this finding. Add a testplan regression before implementing and exercise the stated recovery and permission boundaries.
