Remove public access to protected evidence files
QA-125 | P1 | Bug | TODO
Review date: 14 September 2026
Scope: Local source snapshot 9e09c901f5f7
Role: Anonymous and unauthorized file readers
Location: /uploads/<storageKey>; protected alternative /api/photos/<encodedStorageKey>
Existing behaviour
The backend publicly mounts config.uploadDir at /uploads before authentication. The host nginx template also aliases that directory, with public caching for 30 days. Storage writes trip photos, receipts and fuel evidence into this same directory. A requester with a known evidence key can therefore bypass the authentication and record-ownership checks on /api/photos. The checked-in configuration establishes this path; deployment state is unverified.
Target behaviour
Serve protected evidence only through authenticated, record-authorized delivery at both application and reverse-proxy layers. Isolate any deliberately public logos in a public-only directory. Ensure known links and cache behavior respect current access.
User impact
Private shipment images and financial receipts are exposed to a known-link requester without the intended account or ownership checks. Random filenames reduce guessing but do not authorize access.
Cause and investigation
storageService.upload writes under config.uploadDir; index.ts:149 serves that root publicly, and nginx-host-vantai.conf:18–23 independently serves the mounted host directory. The protected route revalidates accounts and delegates receipt authorization, but neither alias enters that route. photo-authz.test.ts:205–306 covers protected receipt decisions, not the public alias. Tests were read, not run.
Steps to reproduce
1. Use an isolated synthetic evidence image and record its returned storage key through an authorized workflow.
2. Compare anonymous and wrong-owner requests to /api/photos/<key> and /uploads/<key>, at the backend and configured reverse proxy. The code path predicts public file delivery for the latter; no request was executed in this audit.
Acceptance criteria
1. Anonymous and wrong-owner requests cannot retrieve synthetic protected files through either route or proxy path.
2. The authorized owner and intended office roles can still retrieve the same evidence through the protected path.
3. Keep traversal checks and stable file references; use an explicit public-only asset area if required.
4. Remove public caching of sensitive evidence and verify previously cached responses and revoked-account links.
5. Add regression coverage for both application and proxy configuration; do not substitute filename secrecy for authorization.
Verification coverage
CODE-READ ONLY. The source path was reviewed; the current staging deployment, UI interaction and database side effects were not exercised for this finding. Add a testplan regression before implementing and exercise the stated recovery and permission boundaries.
