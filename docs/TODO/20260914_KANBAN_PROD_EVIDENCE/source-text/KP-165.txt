Distinguish unavailable route assets from a verified new deployment
QA-142 | P2 | Bug | TODO
Review date: 14 September 2026
Scope: Local source snapshot 9e09c901f5f7
Role: All roles, including login and protected routes
Location: App-wide lazy route loading; ErrorBoundary and global chunk-error listeners
Existing behaviour
The handler treats generic dynamic-import fetch failures as stale deployment failures. Every Vite preload-error event also triggers recovery. Without checking connection availability or build identity, recovery deletes every CacheStorage cache and reloads the page. It spends the four-hour recovery allowance before knowing whether a new deployment exists. Both the boundary and global fallback claim 'Phiên bản mới đã sẵn sàng'. A connection or asset-service failure can therefore invoke an unrelated deployment recovery and misleading message.
Target behaviour
Distinguish an unavailable connection/asset service from a verified outdated deployment. For unverified fetch failures, show truthful internet-required or service-unavailable recovery with an explicit retry, coordinated with QA-140. Reserve bounded deployment refresh for sufficient evidence of an outdated build, and limit any cleanup to identified application assets. Keep the app internet-only; do not restore offline fallback or mutation replay.
User impact
An asset request failure can cause an unnecessary full reload and removal of unrelated origin caches while telling the user a new version exists. It also consumes the recovery window, so a later real stale-build failure may receive only a fallback. No lost draft, cache-dependent feature failure or live outage is claimed.
Cause and investigation
frontend/src/lib/chunk-error.ts:25–29 classifies by message; 85–88 handles any vite:preloadError. Lines 53–73 delete all cache keys and reload after setting the cooldown, without availability/build evidence. Lines 42–50 and components/shared/ErrorBoundary.tsx:32,43–52 render the unsupported new-version message. main.tsx:23 installs the global handler and App.tsx defines lazy route imports.
Steps to reproduce
1. In a controlled browser test, keep the deployed build unchanged and open a lazy route whose JavaScript asset has not loaded. Block that asset request or make its service unavailable; separately exercise a known offline connection.
2. Observe a matching dynamic-import failure or Vite preload-error event. The inspected path predicts blanket CacheStorage deletion, cooldown consumption and page reload, without a build comparison.
3. Check the recovery text, then test a genuinely outdated tab against a new deployment. These runtime cases are proposed regression scenarios, not executed staging findings.
Acceptance criteria
1. Connection and asset-service failures do not claim a new version, indiscriminately purge caches or immediately force a deployment reload. Provide a clear unavailable state and explicit retry; connectivity indicators alone must not be treated as proof that the asset service works.
2. A verified outdated build has a bounded refresh path with loop protection and a truthful fallback if assets remain unavailable. Unrelated connection failures must not consume that deployment-recovery allowance.
3. Any retained cache cleanup targets only relevant application assets and agrees with QA-141's offline-worker retirement. Never reintroduce cached offline business operation, queued commands or automatic mutation replay.
4. Add cases for unchanged-build network failure, asset-service failure, genuine stale deployment, repeated failure and exhausted recovery in both the React boundary and global event paths. Check compact, accessible recovery text and retry at phone, tablet and desktop widths.
