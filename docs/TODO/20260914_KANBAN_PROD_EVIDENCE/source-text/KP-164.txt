Retire the offline service worker cache and background sync with an upgrade migration
QA-141 | P2 | Enhancement | TODO
Review date: 14 September 2026
Scope: Local source snapshot 9e09c901f5f7
Role: All roles and previously installed browser profiles
Location: All staging routes at https://vantai.tingting.vip; worker /sw.js, including installed app launches and notification opt-in
Existing behaviour
The application registers a worker that can reopen a cached shell when navigation fails and supplies cached static assets. It also schedules journey-board polling using a token mirrored into Cache Storage. Removing only the command queue or main registration leaves existing worker registrations, caches and periodic tags; push opt-in has a second registration path. The polling handler reads data and emits notifications; it does not replay writes.
Target behaviour
Remove worker-provided offline application responses and periodic background sync. Ship an upgrade path for existing installations. Prefer a minimal push-only worker at the existing URL/scope, preserving ordinary push and install metadata while deleting the retired cache/polling code and token mirror. Coordinate release with QA-139 command-queue removal and QA-140 internet-required UI.
User impact
A partial removal can leave returning users on an offline-capable shell, recreate retired caches, or re-register obsolete behavior through notification opt-in. Blanket worker deletion would also disrupt unrelated push subscriptions.
Cause and investigation
Confirmed source coupling: offline fetch handling, periodic polling and push share one worker; startup and notification opt-in both register it. Token module initialization independently recreates the retired cache. These are migration dependencies, not a reproduced deployment failure.
Steps to reproduce
1. Proposed upgrade test: use the previous build, visit several routes, enable available periodic sync and push, and retain two open tabs plus the existing worker/cache state.
2. Deploy the online-only build and reconnect/refresh the old profile. Inspect worker lifecycle, owned caches, periodic tags and both startup/notification registration paths.
3. Disconnect after upgrade and reopen cached routes or the installed app; reconnect and verify direct online operation. Repeat in a fresh profile and with unsupported periodic-sync APIs.
Acceptance criteria
1. Neither registration path installs offline fetch fallbacks or periodic journey polling. Remove the token-cache producer and count metadata consumer together.
2. Migration removes only identified TransTing offline caches/entries and the refresh-journey-board tag; unrelated caches, normal authentication and ordinary push remain intact. Repeated migration is safe and does not recreate retired storage.
3. Previously controlled tabs converge to the new worker without reload loops; no cached application response restores offline operations. QA-140 supplies the internet-required state where the application is loaded.
4. Add worker/migration tests and verify old-profile, multi-tab, fresh-profile and installed-app upgrades in Chrome. Verify notification delivery/click navigation after migration and no queued mutation replay, coordinated with QA-139.
Verification coverage
CODE-READ ONLY. The source path was reviewed; the current staging deployment, UI interaction and database side effects were not exercised for this finding. Add a testplan regression before implementing and exercise the stated recovery and permission boundaries.
