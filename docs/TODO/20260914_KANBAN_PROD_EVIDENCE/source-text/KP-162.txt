Report completed trip financial edits as saved without a false approval queue
QA-137 | P2 | Bug | TODO
Review date: 14 September 2026
Scope: Local source snapshot 9e09c901f5f7
Role: Admin / Manager with trip-edit permission
Location: /trips/:id/edit → PUT /api/trips/:id/actuals
Existing behaviour
A completed-trip financial edit applies in the backend request and returns an applied action. The frontend treats actionKind=TRIP_FINANCIAL_CHANGE alone as pending, skips immediate trip-cache replacement and displays 'Yêu cầu điều chỉnh đã được gửi đến hàng chờ kiểm tra và phê duyệt.' This tells the user to expect a review queue although the change is already applied. The edit form's own reason section correctly says the update applies immediately.
Target behaviour
Complete the authorized direct-save flow and report the actual saved result. Return or retrieve the resulting trip/version, update the detail view and remove the false pending-review success state. Keep ordinary validation, permissions, reason/audit history and conflict handling; do not introduce an approval step.
User impact
Users can wait for a nonexistent review or retry a correction that already changed the trip's financial data. The conflicting messages make the committed outcome unclear.
Cause and investigation
frontend/src/hooks/use-trip-form-submit.ts:399–410 uses actionKind as a pending-state test. backend/src/routes/trips/figures.ts:98–119 directly invokes autoApplyGovernanceAction and returns its result at 136–137. adjustment-governance.service.ts:777–800 returns the action, while governance-action-core.service.ts:238–247 marks it APPROVED/applied. The returned shape retains the actionKind, so the stale frontend branch is reachable.
Steps to reproduce
1. In a controlled test, open an editable completed trip, change a financial figure and enter a valid adjustment reason. Save with valid version and other required inputs.
2. Trace the actuals response: the domain change applies in-request and the response action has TRIP_FINANCIAL_CHANGE plus final applied state.
3. Observe the frontend success toast claims the change went to a check/approval queue. Read back the trip to confirm the direct saved result. This runtime scenario is proposed, not executed in this audit.
Acceptance criteria
1. Successful completed-trip edits show a truthful direct-save result and the resulting figures/version without a pending-review message or queue dependency.
2. Use an explicit API result contract; do not infer pending status from actionKind or pretend to approve a request in the UI.
3. Preserve reason, authorization, validation, idempotency and version-conflict recovery. Distinguish a committed financial update from a later attachment/container/instruction failure.
4. Add frontend coverage using the real applied-action response shape and verify save/readback in desktop, tablet and phone flows. Existing backend direct-apply tests must remain valid.
Verification coverage
CODE-READ ONLY. The source path was reviewed; the current staging deployment, UI interaction and database side effects were not exercised for this finding. Add a testplan regression before implementing and exercise the stated recovery and permission boundaries.
