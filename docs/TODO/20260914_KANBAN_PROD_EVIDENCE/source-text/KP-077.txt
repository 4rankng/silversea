Require current driver ownership before deleting trip photos
QA-126 | P1 | Bug | TODO
Review date: 14 September 2026
Scope: Local source snapshot 9e09c901f5f7
Role: DRIVER, including a former assignee
Location: POST /api/upload/trips/:tripId/photos/:type/delete
Existing behaviour
The delete route checks the trip, photo type and key, optional container link, and COMPLETED status. It obtains the caller only for audit/idempotency metadata. It never checks whether the DRIVER currently owns the trip before removing the photo row and scheduling file deletion. DRIVER has upload:write; POST maps to write, so the enclosing policy permits this route. A known key for another eligible trip is sufficient for the code path to reach deletion.
Target behaviour
Require current trip ownership before deleting a photo or scheduling cleanup. Deny another driver, a former assignee or a driver without a profile without changing evidence. Preserve authorized owner deletion, office permissions and idempotent retries.
User impact
A driver retaining a known photo key after reassignment could remove another driver’s container, seal or delivery-note evidence.
Cause and investigation
ContainerInstancesCard.tsx:323 calls this endpoint. Auth and Casbin reach upload.ts:597–608; deletion occurs at 656–657 without an ownership predicate. Adjacent upload and photo-read paths call checkDriverTripPhotoAccess (upload.ts:494–505,705–718), demonstrating the missing boundary. q23-upload-idempotency.test.ts:164–177 injects ADMIN; its 403–435 deletion test covers replay and cleanup, not cross-driver denial. No tests were executed.
Steps to reproduce
1. Prepare two active drivers and a non-completed trip with a synthetic CONTAINER, SEAL or DELIVERY_NOTE image. Retain the key before assigning the trip to the second driver.
2. As the first driver, submit the delete command with that trip, key and a fresh Idempotency-Key. The source reaches deletion without current ownership; this destructive request was not executed during review.
Acceptance criteria
1. Current owner deletion succeeds once; a retry converges on the same result.
2. Different, former-assignee and no-profile drivers receive a consistent forbidden/not-found result.
3. Denied attempts leave photo rows, file bytes and durable cleanup jobs unchanged.
4. Apply the ownership decision at the write boundary so concurrent reassignment cannot invalidate a prior check.
5. Retain valid key/type/container and terminal-state guards; add route-level cross-driver regression cases with the real authentication and role middleware.
Verification coverage
CODE-READ ONLY. The source path was reviewed; the current staging deployment, UI interaction and database side effects were not exercised for this finding. Add a testplan regression before implementing and exercise the stated recovery and permission boundaries.
