## SIL-644 (id 749) — the cargo-weight dead end

### Option implemented: (a), encoded as "trip still CREATED = the assignment window"

Codebase facts that decided it (verified in source):
- `assignFulfillmentPlate` (dispatch plan) creates NO trip row — "đã điều xe" (planned plate) leaves the container
  fully editable today (no live trip → no guard fires). That state was never the dead end.
- `POST /shipments/:id/dispatch` (Phát lệnh) creates the trip **inside the pricing transaction**
  (`dispatch-planning-commands.service.ts:731` + `lockShipmentFreightRate(tx, {requirePrice:true})` at :807): a
  weightless lot is refused and the whole order rolls back — the "Thiếu trọng tải" 409 is the designed backstop
  (card 20260922_58 ruling 4c).
- The staging lot 285 state (409 on Phát lệnh AND weight locked) is only consistent with a live trip whose status
  is still `CREATED` — the order was issued (trip exists) but its price never completed. Every lock in the tree
  keyed on "trip exists", so that in-between state was a permanent dead end.

**Decision:** a live trip still in `CREATED` is an assignment awaiting completion of Phát lệnh — cargo measures
(trọng tải / CBM, the exact price input) and identity fields stay writable there; once the trip has LEFT `CREATED`
(`IN_TRANSIT`/`COMPLETED`) the container is locked with the existing message. Option (b) (block the assignment)
would NOT have unstuck the reported lot — it was already in the issued-trip state.

### The exact state distinction (file:line)
- `backend/src/services/shipment-containers.service.ts:516-528` — `reconcileShipmentContainersWithFulfillmentGuard`
  now 409s only on `issuedFulfillments` (`tripId != null && tripStatus !== 'CREATED'`); the old blanket
  "any trip → 409" is gone.
- `backend/src/services/shipment-containers.service.ts:530-560` — assigned-but-not-issued: the fulfillment
  SURVIVES the reconcile when its container survives the batch (same id) and no guarded plan field changed
  (loại cont / tuyến / lịch hẹn / nhà máy / phân loại — the same guarded set the workspace line write enforces
  value-aware); removing an assigned container still refuses ("Không thể bỏ container đã được điều xe…").
- `backend/src/services/shipment-containers.service.ts:562-594` — only UNASSIGNED fulfillments are canceled
  (the pre-existing refresh mechanism); canceling the dispatcher's CREATED-trip assignment would re-create the
  dead end.
- `backend/src/services/cus-shipment-workspace-writes.service.ts:406-416` — the ledger container-line write's
  value-aware trip guard no longer counts weight/volume as blocking mutations while `trip.status === 'CREATED'`.
- `backend/src/services/cus-shipment-workspace-reads.service.ts:743-771` — `withIssuanceWindowFieldAccess`
  upgrades `cargoWeightKg`/`cargoVolumeCbm` to `DIRECT` when `line.tripStatus === CREATED` (no active lock, role
  ADMIN/MANAGER/CUS/DISPATCHER) and is wired at BOTH ledger projections — the workspace detail line (:783, the
  inline editor's `line.fieldAccess`) and the flat list row (:1323, the cell affordance), so they can never
  disagree.
- `shared/src/shipment-effective.ts` — `sameInstantOrNull` (the appointment-equality law used by the guard,
  `undefined` = keep-stored, `null` = clear, instant equality offset-agnostic), exported via `shared/src/index.ts`.

### Files outside my lane, edited with reasons (unclaimed by any lane in the ownership map)
- `backend/src/services/cus-shipment-workspace-writes.service.ts` — the ledger inline editor's save endpoint.
  Without relaxing its weight/volume clause the FE field would have opened and then 409'd ("Container đã gắn
  chuyến xe") — a worse dead end. Surgical: only the two cargo-measure clauses are gated on the issued state.
- The dispatch **"Sửa điều phối" dialog weight field** (`frontend/src/features/dispatch/detailed-plan/**`,
  SIL-647/648/638-FE lane — NOT touched): the dispatcher's reassign editor has no weight field. With this fix the
  weight does not need one there — the Chứng từ ledger line (and the lot worksheet) fills it in the assignment
  window, and the dispatch dialog keeps editing vehicle/schedule only. If the owner wants a weight field in that
  dialog too, the required change is: `frontend/src/features/dispatch/detailed-plan/` plan-save editor — add a
  Trọng lượng input that PATCHes the container line via the same CUS container-line endpoint; it must NOT write
  `trips.cargo_weight_kg` directly (the trip's weight is stamped from the container at issue/re-issue).
