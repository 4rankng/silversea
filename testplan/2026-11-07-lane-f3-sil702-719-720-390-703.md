## Fixes

- **SIL-702** — the LCL row's "Phân loại" pair was narrowed to "Lẻ" only on
  2026-10-06 (`007352d6`) because the DB check
  `shipment_fulfillments_lcl_dispatch_classification_check` (added **2026-08-20**,
  i.e. BEFORE the "Lấy Lẻ" classification existed) pinned an `LCL_SHIPMENT`
  row to `'LCL'`, so saving "Lấy Lẻ" died on the constraint as a raw 23514 →
  HTTP 500. The workaround removed the option instead of widening the
  constraint — and the dialog's own hint kept promising "Lẻ hoặc Lấy Lẻ".
  The documented law is `testplan/flows/02-dieuvan-dispatch.md` §2.13
  (2026-10-03) + `TC-DV-DISPATCH-053` ("Dòng LCL chỉ chọn được Lẻ/Lấy Lẻ").
  Fix = migration `20261107094500_lcl_fulfillment_lcl_pickup_classification`
  (a pure widening — no data is restated) + the write-path guard relaxed to
  the pair (`backend/src/services/dispatch-plan-classification.ts`, the shared
  owner) + the select offering the pair again.
- **SIL-719** — the shared contract already accepts a non-negative volume
  (`shipmentVolumeCbm`, "số không âm"); only the LCL create form's readiness
  check blocked `<= 0`. The form now validates with the shared schema (the
  single owner), so 0 saves and a value the API would reject never leaves the
  browser.
- **SIL-720** — the lot page's SỐ TỜ KHAI cell was frozen in view mode, so a
  CUS had to open "Sửa" (the whole form) or move to `/shipments-detail`. The
  cell is now the SHARED `DeclarationInlineCell` (the dispatch grid's editor,
  migrated onto it) — click the value, edit, Enter saves through
  `POST /shipments/cus-workspace/:id/containers/:containerId`; the workspace
  re-reads the lot so the FB-109 auto-copy shows on THIS surface (the reported
  "2 dòng có, 1 dòng trống" was exactly this stale read).
- **SIL-390** — **no code change**: the FCL field-set of "Phân bổ nhà xe" has
  no plate field by contract (FB-066 lần 3, card 201026101600: "FCL cont
  field-set: NOT APPLICABLE (không có ô BKS)"; the carrier row can cover
  several containers → several plates). The wire contract
  (`shipmentCarrierAllocationSchema`) carries no plate either. The quick-add
  exists on every surface that owns a plate. The ruling is reported on the
  ticket with the evidence + a pin (`DispatchAllocationPopover.fb066-quickadd-contract`).
- **SIL-703** — **no code change**: the reporting-policy surface EXISTS at the
  ADMIN-only `/config/app-settings` → tab "Chính sách báo cáo" (never deleted —
  `58557c19` is an ancestor of HEAD). SIL-197 already fixed the Cmd-K
  description; the entry is pinned so it stays discoverable.

### SIL-702 end-to-end (the save path against a REAL migrated database)

The shared dev database was deliberately **not** migrated (an unknown row in the
shared `__drizzle_migrations` table would make another lane's pending migration
look applied). Instead `qa/2026-11-07-lane-f3/probe-sil702-end-to-end.mjs`:

1. clones `silversea` → `silversea_f3` (a throwaway database) and applies the
   lane migration to the clone;
2. runs THIS worktree's backend against the clone (`:3005`);
3. logs in (Điều vận), picks an LCL plan row, saves "Lấy Lẻ" through
   `PATCH /api/shipments/dispatch-detail-plan-rows/:id/plan` → **200** with
   `classification = LCL_PICKUP`;
4. reads the row back: `LCL_SHIPMENT | LCL_PICKUP` (`sil702-end-to-end-db-read.log`);
5. saves a cont model on the same row → **409** "Phân loại không hợp lệ cho lô
   Hàng lẻ. Lô hàng lẻ chỉ dùng phân loại "Lẻ" hoặc "Lấy Lẻ".";
6. drops the clone and stops the probe backend — the shared stack is untouched.
