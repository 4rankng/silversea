## TC1 — window-by-shift + stale set

### Root cause 1 (holder keyed on the lot's scheduled date)
`dispatch-plan-conflict-scan.service.ts` — both rig-holder scans
(`scanPlanRowHolders`, `scanLclPlanRowHolders`) measured every holder by the LOT's scheduled
slot: `coalesce(customerAppointmentAt, closingAt, plannedReturnAt)` and the
`expectedDeliveryDate` whole-day fallback. A holder that was already ISSUED at
08:00–12:00 (the window the dispatcher entered in the dialog, stored on
`trips.plannedStartAt/plannedEndAt`) still claimed the lot slot, so a ca chiều 14:00
assignment was refused 6 hours apart (QA: 1RA 08:00 saved, 1RB 14:00 rejected; 12/12 dialog
datetime still rejected).

Law implemented (both scans, identical):
- holder start = `coalesce(live-trip planned_start_at, lot slot, day fallback)`;
- holder end = `coalesce(live-trip planned_end_at, live-trip start + 8h, fulfillment plannedEndAt, legacy lot coalesce)`;
- live trip = latest (id desc) non-deleted trip in `CREATED`/`IN_TRANSIT`;
- a holder riding its own trip window is STRONG evidence (`fallbackSlot` requires
  no trip start and no container appointment).

Issue/reissue and the trip-form guards already compared the dialog window; the plan-save
path's SAVING-side window still resolves from the row's lot slot because
`UpdateDispatchDetailPlanInput` carries no start field (only "Giờ trả hàng") — the saving
side has no dialog datetime to use by schema. The measured failure is the HOLDER side and
is fixed there; the saving-side issue window is the dialog datetime
(`issueOrderCreateOrUpdate` → `parseIsoWithZone(input.plannedStartAt)`).

Shift law unchanged and pinned: strict overlap only (`tripClaimWindowOverlaps`), 8h
open-ended claim, IN_TRANSIT vehicle stays blocked (1RD case), touching edges free.

### Root cause 2 (the stale/hidden set — SHP-2610-00267/-00322/-00323)
The same holder scans filtered only `shipmentFulfillments.canceledAt is null`. The plan-row
READ (`dispatch-planning-detail-plan-read.service.ts:201-203`) shows rows only for
non-deleted shipments in `READY_FOR_DISPATCH / DISPATCHED / IN_TRANSIT / COMPLETED` — the
scans had neither filter, so fulfillments carrying a plate on a NEW/PENDING_DATE/CANCELED
or deleted lot were invisible in the grid yet kept blocking assignments.

Fix: `OPERATIONAL_HOLDER_SHIPMENT_STATUSES` (mirrors the read verbatim) + `isNull(shipments.deletedAt)`
applied to BOTH scans (`dispatch-plan-conflict-scan.service.ts:80, 277, 334`). Trips-based
scans already filter by trip status/deletedAt; the day-claim warn scans only count COMPLETED
trips, which appear in the trip list, so no hidden set exists there.

## TC2 — classification mismatch message

`assertPlanRowRigAvailable` (dispatch-planning-detail-plan.service.ts:877-891 pre-edit)
checked `classificationMismatchShareBlockMessage` over `tripConflicts` (dispatched trips)
only. The Kẹp holder is ALSO a plan-row holder — the holder scan keeps issued rows until a
trip completes — so the ĐƠN assignment hit `planRowBlocked` from the plan-row scan and
answered the generic overlap toast; the mismatch message never ran.

  (`RIG_OVERLAP_COMPLETED` code, confirm proceeds) but both warn sites now use
  `MIXED_DECLARATION_KEP_WARN_MESSAGE` = DOC wording + " Vẫn lưu?"
  (trip-pair-rules.service.ts:255; availability:467; detail-plan:942).

Verbatim strings:

## TC6(1) — 40ft Kẹp hard block

### Leaking path
`kepContainerSizeBlockMessage` fired ONLY in the pairing core
(`createTripPairCoreInTx`, trip-pairs.service.ts:562). The dispatch lane QA used never
creates a pair row: assign (plan save / plate endpoint) and issue/reissue
(`issueOrderCreateOrUpdate`) had no size law at all → lot 00048 (40ft Kẹp) saved.

Fix — new shared guard `assertKepIssuingContainerClass`
(dispatch-resource-availability.service.ts:95): classification `DOUBLE` + declared
container class ≠ 20 → hard `409 KEP_CONTAINER_SIZE_BLOCK_MESSAGE`
(`Cặp kẹp chỉ áp dụng cho đúng 02 container loại 20ft`); undeclared size (no type link)
keeps "bổ sung sau" and skips. Wired on every dispatch-write path:
- issue/reissue: dispatch-planning-commands.service.ts:389 (inside `issueOrderCreateOrUpdate`, so Phân xe lại is covered);
- atomic plan save: dispatch-planning-detail-plan.service.ts:1161 (effective classification `input.classification ?? fulfillment.dispatchClassification`);
- legacy plate endpoint: dispatch-planning-detail-plan.service.ts:558;
- pairing core unchanged (both-legs law stays for pair creation).

## TC6(2) — soft weight warning actually fires

### Leaking path (the path QA used: issue of both 28/12 legs)
The weight guard ran only inside the overlap-conflict carves of
`assertResourceAvailability` and required provable weights:
1. no overlap conflict → gate never evaluated (the carves are the only callers);
2. incoming weight: `authoritativeCargoWeightKg` reads ONLY
   `shipmentContainers.cargoWeightKg` for container-linked legs — QA's 60,000 kg on the
   lot level read null;
3. partner weight: read only from `tripContainers.cargoWeightKg` — null on the same data.
Result: `unprovable` → silent save with the success toast.

Fix (soft contract unchanged — refuse once, confirmed retry via
`kepWeightWarningConfirmed=true` proceeds):
- co-rider gate (availability:367-424): when the issuing leg declares KẸP (20') and no
  overlap blocking row exists, the guard scans same-truck `CREATED`/`IN_TRANSIT` trips of
  the same Vietnam business day, admits exactly the declared share partner or the
  mixed-declaration candidate, probes the single-20'-shell shape, and runs the same
  `kepPairWeightVerdict`/`kepWeightGuardOutcome` law → `409 KEP_WEIGHT_WARNING` +
  `Tổng tải trọng hàng ước tính có thể vượt tải trọng cho phép của phương tiện, Điều vận vui lòng kiểm tra lại`;
  runs only for KEP — Kết hợp (sequential reuse) never weight-gates;
- incoming weight fallback at the issue call (commands:712):
  `cargoWeightKg: cargoWeightKg ?? shipment.cargoWeightKg` — gate arg only; trip storage
  keeps `authoritativeCargoWeightKg`;
- partner weight fallback at all three carve sites + the co-rider gate:
  `containers[0].weight ?? partnerShipmentWeight` (conflict select now carries
  `shipments.cargoWeightKg`).

FE contract UNCHANGED: field `kepWeightWarningConfirmed` (boolean, issue endpoint
`POST /api/shipments/:id/dispatch`), error code `KEP_WEIGHT_WARNING`, exact copy above,
retry semantics = confirmed retry saves. The plan-save endpoint deliberately does NOT
weight-gate: its route schema (`dispatch-planning.routes.ts`, another lane's file) has no
confirm flag, so a first-attempt 409 there would be a dead end. Required if QA wants the
warning at plan-assign time: add `kepWeightWarningConfirmed: z.boolean().optional()` to
`atomicDispatchPlanEditSchema` + a pair-weight call in `assertPlanRowRigAvailable` — reported, not edited.
