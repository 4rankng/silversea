## rb2 re-verify (2026-10-19 21:23) — driver hardening: racy DOM-clear

Product code unchanged at HEAD `c17b94e1` (fix `c56b5928` already landed).
rb2 evidence: `qa/2026-10-19_card191026181942-rb2/` (5 screenshots +
`_ui-driver.log` + `_db-proof.txt`), gates `qa/2026-10-19_card191026181942-rb2_tsgo.log`
(EXIT=0) + `...rb2_vitest.log`/`...rb2_vitest-final.log` (60/60; the first
default-parallel run threw 3 load timeouts on a busy machine — sequential rerun
green, no assertion failure).

Root cause found while re-driving DV3 A2: the driver's `el.value = ''`
direct-DOM clear races React's controlled restore — under load the seeded
value came back between the clear and the first keystroke, the typed text
APPENDED to it, and the doubled string rode `onCustomValue` into state and
the DB (dev residue read back as a doubled seed `60C-QA94260C-QA942` in the
first rb2 attempt; product truth-wins seeding displayed it faithfully). Fix
is driver-side only: clear through the field's own Xoá affordance (fires
`onChange('')` + `onCustomValue('')`), select-all+type-over fallback, and a
pre-save guard that refuses to persist any value ≠ `60C-QA942`. Re-run:
11/11 PASS, DB row 110539 `actual_truck_no=60C-QA942` single
(`updated_at 2026-10-19 13:23:08`). Minimal repro probes confirmed the dialog
never doubles on its own (cold + warm vite, options loaded async, value ∈
fleet options).
